# Scope-state review — write loss, stale reads, bypass

Assumes `state_lock` is the exclusive fcntl sidecar the `scope_state_store` docstring describes; if it is ever made per-path reentrant, both deadlock items become safe instead.

## Q1 — every concrete way a write is lost or stale data is returned

1. **`discard_state` writes outside every lock.** It builds a fresh `ScopeStateStore` and `unlink`s: no `_batch` check, no `state_lock`. `T1: with state_batch(k):` loads `{a:1}`, holds the flock · `T2: discard_state(k)` unlinks · `T1` clean exit → `atomic_write_json` → **the deleted file is resurrected** (a reset that never happened). Reverse: `T1: _mutate` loaded `{a:1}`, has not written · `T2` unlinks · `T1` writes `{a:1,b:2}` → **the delete is lost**. `discard()`'s `except OSError: return False` also reports a failed unlink as "there was none", so a purge that did nothing looks like one that had nothing to do.
2. **A batch is invisible to other threads' reads and blocks their writes.** `_read()` on any thread whose `_local.batch is None` reads the file, not the open payload: `T1: with state_batch(k): set_state(k,a,1)` · `T2: get_state(k,a)` → the old value · `T2` decides from it and writes → a stale-derived result (wrong dedupe, wrong position) even though `T2`'s own read-modify-write merges honest keys. `state_snapshot` has the same blind spot, and `delete_state` inside a batch returns `True` while `T2` still reads the key.
3. **Deadlock-as-loss when the batch body waits on its own writers.** The lock is held across the whole `yield`, so every concurrent `set_state` blocks. In the docstring's own scenario — `invoke_parallel`, 32 workers sharing one `WorkflowScope` — a `state_batch` opened on the joining thread hangs: workers block on the holder, the holder waits on the workers, nothing ever commits and **every write in the batch is lost**.
4. **`_ensured` is never invalidated.** `_state_store` skips `ensure_scope` once the id is memoised: `set_state` (ensures) · `delete_scope` · `discard_state` · `set_state` → a state file no record references, and `purge_scopes` walks *records*, so nothing can ever collect it. Same hole if `ensure_scope` raises *after* `_ensured.add(scope_id)` (e.g. `_mutate` on a corrupt `scopes.json`): the id is memoised but no record was ever made.
5. **`_state_stores` is an unguarded check-then-set dict** (get → build → set, no lock). Two threads on a new scope id both see `None`, both build a store, and the loser's object is returned to its caller but not cached. Batch state and the reuse guard are per object, so the loser's batch is not the winner's transaction — see Q2.1b.
6. **Silent-empty read** (not racy, still loss): `_load` rejects only a non-dict *top level*, so `{"state": []}` or `{"state": null}` reads as `{}`; the next unbatched `set` then rewrites the file to `{"state": {k: v}}`, dropping every key that was on disk.

## Q2 — does a nested call bypass the batch, and is the lock taken twice?

1. **Bypass — yes, two paths.** (a) `discard_state`: fresh object ⇒ empty `threading.local` ⇒ `_batch is None`, and it never calls `state_lock`; nested inside `state_batch` it unlinks the file the outer batch recreates on clean exit (Q1.1). (b) If the open batch lives on the object that lost the Q1.5 race, every later accessor resolves the *cached* object instead, whose `_batch` is `None` → `_mutate` looks the lock and writes directly, ignoring the open batch; the batch's commit then runs **after** that write and replaces the whole payload with its stale one → the direct write is lost. (On the batch's own thread the direct write instead blocks — item 2.)
2. **Double acquisition by one thread — yes, whenever two `ScopeStateStore` objects exist for a path.** The guard `if self._batch is not None: yield self; return` is per object *and* per thread, because `_batch` reads `self._local`. A second object has an empty `threading.local`, so its `batch()` enters `state_lock(p)` again, and `flock(LOCK_EX)` from a distinct fd blocks even within one process → **self-deadlock**. The `_state_stores` cache hides this on the normal path, until the Q1.5 race, a direct `ScopeStateStore(path)` (as `discard_state` uses), or a second `ScopeStore` over the same file.
3. **On a single object there is no double acquire** — nested `state_batch` reuses the outer batch and in-batch `_mutate` never locks. But the lock *order* inverts: `state_batch` holds the state lock and a `record_step` inside the body then takes `scopes_lock` (`ensure_scope` → `update_scopes`), while `with store.batch(): store.set_state(...)` holds scopes and then takes state. `T1: with state_batch(k): record_step(...)` · `T2: with batch(): set_state(k, ...)` → **classic lock-order inversion, deadlock**.
