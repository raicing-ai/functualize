# 06 — AWS S3

**Level 1, and since 2024 genuinely level 2.** This is the most interesting result in the
evaluation: S3 can now do almost everything our port asks for, and the one thing that
breaks is a mistake in *our* type signature, not in S3.

## 1. Why this used to be a non-starter and no longer is

Two changes, both after this codebase's storage design was written:

| Date | Change | What it unlocked |
|---|---|---|
| Dec 2020 | **Strong read-after-write consistency** for PUT and DELETE, all regions, automatic, free ([announcement](https://www.amazonaws.cn/en/new/2020/amazon-s3-now-delivers-strong-read-after-write-consistency-automatically-for-all-applications/)) | you can read back what you just wrote |
| Aug + Nov 2024 | **Conditional writes** — `If-None-Match: *` (create-only) and `If-Match: <etag>` (replace-if-unchanged), returning `412 Precondition Failed` ([PutObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutObject.html)) | **compare-and-swap** |

Before 2024, building a lock on S3 meant DynamoDB alongside it. That is now obsolete for
the single-object case, and the industry has moved:

- Apache Iceberg's `DynamoDbLockManager` is **deprecated**
  ([javadoc](https://iceberg.apache.org/javadoc/1.1.0/org/apache/iceberg/aws/dynamodb/DynamoDbLockManager.html)).
- Terraform shipped **native S3 state locking** (`use_lockfile = true`) explicitly to
  replace its DynamoDB locking backend.

So "S3 has no locking" is a true statement about 2019 and a false one about today.

## 2. Mapping `StoreSubstrate` onto S3, method by method

This is the useful exercise: our port has six methods
(`src/functualize/_types/protocols.py:760-880`). Here is each one against S3.

| Port method | S3 implementation | Works? |
|---|---|---|
| `read(key) -> Stored \| None` | `GetObject`; `404` → `None`; revision = the `ETag` | ⚠️ see §3 |
| `write(key, payload, *, expect=None) -> bool` | `PutObject` with `IfMatch=<etag>`; `412` → return `False` | ✅ exactly the semantics the docstring describes |
| `write(..., expect=None)` on a new key | `PutObject` with `IfNoneMatch="*"` | ✅ |
| `lock(*keys)` | **no-op** | ✅ — the port already allows this: "May be a no-op for a backend that offers no mutual exclusion, which is why `write` takes `expect` and returns a bool" (`protocols.py:842-845`) |
| `clear(key) -> str \| None` | `CopyObject` to a sidecar key, then `DeleteObject` | ✅ |
| `delete(key) -> bool` | `DeleteObject` with `IfMatch=<etag>` (GA on general-purpose buckets Sept 2025) | ✅ |
| `describe() -> str` | `s3://bucket/prefix` | ✅ |

**Five of six map cleanly.** The port was designed for this — the docstring says so
outright: "A key is not a path. `"fresh"`, `"scopes"`, `"runs"`, `"scope-state/<scope-id>"`
— a substrate over SQLite **or S3** maps those however it likes" (`protocols.py:773-776`).

## 3. The one thing that breaks — and it is our bug

```python
@dataclass(frozen=True)
class Stored:
    data: dict[str, Any]
    revision: int          # <-- here
```
— `src/functualize/_types/protocols.py:755-756`

The docstring directly above it is correct and the type directly contradicts it:

> "revision: An **opaque token** identifying *this* content. Compare it, pass it to
> `StoreSubstrate.write`; **do not order it or do arithmetic on it**. A filesystem derives
> one from the bytes, **a remote store from its own row version**, and neither meaning
> survives the other."

An S3 ETag is a quoted hex string, e.g. `"d41d8cd98f00b204e9800998ecf8427e"`, and for
multipart or SSE-KMS objects it is not even an MD5
([Object reference](https://docs.aws.amazon.com/AmazonS3/latest/API/API_Object.html)).
It cannot be an `int`.

**This is a finding, not a blocker.** The fix is one character-level change in one file —
`revision: int` → `revision: str`, or a `Revision = str | int` alias — plus the SQLite
substrate returning `str(row[1])`. But it is worth naming precisely, because it is
evidence for a general claim this folder makes: *the port was designed with a remote
backend in mind and was never tested against one, so the places it does not quite fit are
exactly the places nobody had to look.*

Nothing outside a substrate does arithmetic on a revision — the docstring forbids it, and
`plugins/functualize-state-sqlite/src/functualize_state_sqlite/substrate.py:112` is the
only place a revision is constructed. Verify before changing it:

```console
$ grep -rn '\.revision' src/functualize plugins --include=*.py
```

## 4. What S3 still cannot do

### 4.1 No atomic multi-object write, and AWS says so plainly

> "Updates are key-based. **There is no way to make atomic updates across keys.** For
> example, you cannot make the update of one key dependent on the update of another key
> unless you design this functionality into your application."
> — [S3 data consistency model](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html#ConsistencyModel)

This matters directly. Defect B3 in
[`../runtime-persistence-engine-owned/03-the-four-defects.md`](../runtime-persistence-engine-owned/03-the-four-defects.md)
is that no code path commits `scopes` and `scope-state/<id>` together. **S3 cannot fix
B3.** It has the same limitation our filesystem substrate has.

The industry workaround is the **manifest swap**, and AWS documents it: write the
immutable content objects first (`If-None-Match: *`, so each is written exactly once),
then do **one** conditional `PutObject` with `If-Match` on a pointer object that names
them. Atomicity lives entirely in that single pointer write; a crash before it leaves
orphaned objects — garbage, not corruption
([Building multi-writer applications on Amazon S3](https://aws.amazon.com/blogs/storage/building-multi-writer-applications-on-amazon-s3-using-native-controls/)).

That pattern is implementable here, and it would change the storage layout materially
(content-addressed immutable documents plus one mutable pointer). It is a design decision,
not a configuration flag, and it should not be smuggled in under "add an S3 backend".

### 4.2 No server-side lease expiry

S3 gives you compare-and-swap on an object. It does not give you a TTL, and it will not
expire a lock for you. Gunnar Morling's analysis of exactly this — building leader
election on S3 conditional writes — is blunt about the limit:

> "leader election will only ever be **eventually correct**" … "checking lock validity and
> performing the leader's actual work is **not atomic**, no matter how hard you try."
> — [Leader Election With S3 Conditional Writes](https://www.morling.dev/blog/leader-election-with-s3-conditional-writes/)

**Good news: our design already assumes this.** The generation is the mechanism and the
expiry is only a hint about *when* a claim becomes takeable:

> "The generation is the mechanism. The expiry is only how a dead runner's claim
> eventually becomes claimable — it decides *when* someone may take over, never *who
> wins* once they have."
> — `src/functualize/_primitives/lease.py:27-29`

That paragraph was written about a filesystem. It is exactly the property that makes
S3 viable: we never needed a server-side lease, only a fenced write. Which S3 now has.

### 4.3 Portability across "S3-compatible" stores is not free

| Backend | `If-None-Match: *` | `If-Match` | Note |
|---|---|---|---|
| AWS S3 | ✅ | ✅ | the reference |
| Cloudflare R2 | ✅ (superset — arrays, weak ETags) | ✅ | but see `05-cloudflare.md` §C on the undocumented atomicity question |
| MinIO | ⚠️ **rejects the wildcard `*`** | ✅ | [minio#20346](https://github.com/minio/minio/issues/20346) |
| Google Cloud Storage | ❌ different header: `x-goog-if-generation-match: 0` | via generation-match | S3-style header reported silently ignored ([ClickHouse#115266](https://github.com/ClickHouse/ClickHouse/issues/115266)) |
| Ceph RGW | unknown | unknown | [open feature request](https://github.com/ceph/s3-tests/issues/583) |

A plugin advertising "S3-compatible storage" would be making a claim it cannot keep. Name
the backend (`functualize-store-s3`), and let a `StoreProfile` declare what it verified.

## 5. Cost, for our actual workload

Five documents, updated a handful of times per job run. US East (N. Virginia),
[S3 pricing](https://aws.amazon.com/s3/pricing/):

| | Rate |
|---|---|
| PUT / COPY / POST / LIST | **$0.005** per 1,000 |
| GET | **$0.0004** per 1,000 |
| Storage | **$0.023** per GB-month |
| Minimum billable object size | none on S3 Standard |
| Minimum storage duration | none on S3 Standard |

A workflow doing 200 state transitions costs roughly 200 PUTs + 200 GETs ≈ **$0.0011**.
A thousand such runs a month: **about a dollar.** Storage for five JSON documents is
unmeasurable.

Failed conditional writes are still billed — "you are only charged existing rates for the
applicable requests, **including for failed requests**" — so a retry storm costs PUTs. At
$0.005/1,000 that is cents even under heavy contention; you will hit `503 SlowDown` (the
per-prefix ceiling is ~3,500 PUT/s) long before it becomes a cost line.

**Do not use S3 Standard-IA or One Zone-IA**: 128 KB minimum billable object size and a
30-day minimum storage duration mean our small, frequently-rewritten documents would be
billed as 128 KB each and incur early-deletion charges on every update.

**Latency is the real cost, not dollars.** Each `write()` becomes an HTTPS round trip.
From outside AWS that is tens to low hundreds of milliseconds. Our write path is
read-modify-write under a lock, so a single scope mutation is at minimum GET + PUT. A
workflow with 200 transitions spends a meaningful fraction of a minute in network I/O
that the filesystem substrate does in microseconds. That is the honest trade and it
should be in the plugin's README, not discovered by a user.

## 6. Two retry facts worth building on

**A retried conditional PUT cannot double-apply.** If your PUT succeeded but the ACK was
lost and you retry: with `If-None-Match: *` the retry now sees the object exists and
returns 412; with `If-Match: <old-etag>` the ETag has already moved, so it also returns
412. The correct client rule is therefore:

> **412 on a retry means "go re-read", not "it failed".**

**`409 ConditionalRequestConflict` is a different error from `412`.** 409 signals a
genuine race at the moment of write and AWS says to retry it (re-fetching the ETag
first); 412 is a settled answer. A substrate that treats them identically will either
give up too early or loop forever.

## 7. S3 Tables and S3 Express — checked, and both are the wrong tool

**S3 Tables** (Dec 2024, managed Apache Iceberg) has real per-table ACID transactions.
It is also: columnar Parquet, reachable only through a query engine or the Iceberg REST
catalog via PyIceberg, with maintenance charges of "$0.05 per GB processed + $0.004 per
1,000 objects" plus "$0.025 per 1,000 objects" monitoring — and observed compaction
delays of **2.5–3 hours**. One published benchmark put maintenance at **29× the
self-managed cost**
([Onehouse analysis](https://www.onehouse.ai/blog/s3-managed-tables-unmanaged-costs-the-20x-surprise-with-aws-s3-tables)).
For five small JSON documents needing sub-second read-after-write, this is not close.
No AWS statement of *multi-table* atomicity was found either, so it would not fix B3.

**S3 Express One Zone** gives single-digit-millisecond latency, supports conditional
writes (and got conditional deletes a year before general-purpose buckets), and is
cheaper per request ($0.00113 vs $0.005 per 1,000). It stores data in **one Availability
Zone**. For a runtime store whose whole purpose is surviving failure, trading durability
for latency is the wrong direction — and the latency that hurts us is the client's
internet RTT, which Express does not remove.

## 8. Verdict

| Question | Answer |
|---|---|
| As a backend store? | **Yes** — technically viable today, as a plugin, five of six port methods mapping cleanly. |
| As a durability provider? | **Level 1 and most of level 2.** Real CAS, no atomic multi-key, no server lease. |
| Does it fix our defects? | **B1 and B4 yes** (fencing gets a real CAS). **B3 no** — cross-document atomicity is exactly what S3 lacks. |
| Blocking work first? | `Stored.revision: int` must become opaque. Trivial, and needed regardless. |
| Should we build it now? | **No** — see `09-verdict.md`. Fix the defects on the substrates we have first; a remote substrate on top of a broken fence inherits the break and adds latency to it. |
